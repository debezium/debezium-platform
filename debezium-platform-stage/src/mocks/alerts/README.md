# Alerting mock data

Fixtures for building/testing the alerting UI without a live conductor. Each
file mirrors the exact JSON shape returned by a conductor alerting endpoint
(`quay.io/mvitale/platform-conductor:alerting`, API `3.7.0-SNAPSHOT`).

Base path: `/api/alerts`

| File | Endpoint | Response schema | Notes |
|------|----------|-----------------|-------|
| `channels.json` | `GET /api/alerts/channels` | `NotificationChannelResponse[]` | **Real** data pulled from the live API. |
| `rules.json` | `GET /api/alerts/rules` | `AlertRuleResponse[]` | **Real** data pulled from the live API. |
| `events.json` | `GET /api/alerts/events?page=0&size=20` | `PagedAlertEventResponse` | **Synthetic**. Page 0 of 3. |
| `events-page-2.json` | `GET /api/alerts/events?page=1&size=20` | `PagedAlertEventResponse` | Synthetic. Page 1. |
| `events-page-3.json` | `GET /api/alerts/events?page=2&size=20` | `PagedAlertEventResponse` | Synthetic. Page 2 (last, 5 items). |
| `status.json` | `GET /api/alerts/status` | `AlertStatusResponse` | Synthetic snapshot of active alerts. |

## What the dataset covers

**Channels (4):** `Platform Ops Email` (EMAIL, enabled), `Data Team Digest`
(EMAIL, enabled), `Slack #cdc-alerts` (WEBHOOK, enabled), `PagerDuty Events`
(WEBHOOK, disabled).

**Rules (12):** varying severity (CRITICAL / WARNING / INFO), 4 comparison
operators (GREATER_THAN, GREATER_THAN_OR_EQUAL, LESS_THAN, NOT_EQUAL), 4
reduce functions (AVG / MAX / SUM / LAST), some multi-channel, some with no
channel, two disabled (`snapshot-stalled`, `snapshot-table-count-anomaly`).

**Events (45):** spread across the 10 enabled rules and 7 pipeline identities
(`test-pipeline`, `orders-cdc`, `inventory-sync`, `payments-stream`,
`users-replication`, `analytics-export`, `audit-log-cdc`), a mix of `FIRING`
(open, `resolvedAt: null`) and `RESOLVED` (with `resolvedAt` +
`durationSeconds`), all three severities, firedAt spread over the last 7 days,
sorted newest-first, paginated at 20/page.

**Status:** 14 firing + 2 pending active alerts, with `firingBySeverity`
counts. Firing entries are consistent with the `FIRING` events in the paged
files (same rule/pipeline/value/threshold/since).

## Notes for wiring up mocks

- Event `status` uses `AlertStateValue` string values: `FIRING` / `RESOLVED`
  in the event history; `activeAlerts[].state` also uses `PENDING`.
- `createdAt` / `updatedAt` on rules/channels reflect the live API (real
  timestamps here; the API returns them populated).
- Query params on `GET /api/alerts/events` (`from`, `to`, `pipelineId`,
  `ruleId`, `severity`, `status`, `page`, `size`) are not pre-filtered in these
  files — filter client-side in your mock handler if you need it, or just serve
  the matching page file for pagination.

## Regenerating

Channels/rules were exported live with:

```bash
curl -s http://platform.debezium.io/api/alerts/channels | jq '.'            > channels.json
curl -s http://platform.debezium.io/api/alerts/rules     | jq 'sort_by(.id)' > rules.json
```

Events/status are generated by `/tmp/gen_alerts.py` (seeded, deterministic).
